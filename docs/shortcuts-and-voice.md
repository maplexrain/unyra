# 快捷键与语音

两个模块各自一份说明：**快捷键**只回答「谁占了哪个组合」，**语音输入**只回答「点一下开始录、说完怎么出字」。

## 快捷键（`lib/shortcuts`）

**只有一份全局监听**：功能通过 `subscribeShortcut` / `useShortcut` 登记，谁占了哪个组合只有一个地方
说得清，冲突检测才有意义。组合键以字符串存进 `setting.yaml` 的 `shortcuts`，改过的才写、没改的用
代码里的默认值；回调分 `down` / `up`（点按型只用 `down`），**自动重复一律忽略**（否则「按住」类功能
会不停重启）。`Ctrl` 在 macOS 上当 `Cmd` 使——一边是 Windows 的写法，一边是 Mac 的
手感，两边都该响。

默认七条：

| 功能 | 默认组合 | 说明 |
| --- | --- | --- |
| 语音转文字 | 按住 `Ctrl+T` | 光标放在任意输入框里即可说话 |
| 保存文档 | `Ctrl+S` | 把暂存区里的改动写进当前这份文档 |
| 文档内查找 | `Ctrl+F` | 正文右上角浮出查找条 |
| 文档内替换 | `Ctrl+H` | 源码视图下展开替换行 |
| 导出文档 | `Ctrl+E` | 与页签栏右侧那颗下载按钮同一件事 |
| 关闭当前标签页 | `Ctrl+W` | 关的是**焦点格**里正看着的那一个，有没保存的改动照旧先问一声 |
| 收起 / 展开右侧栏 | `Ctrl+Q` | 与骑在分割线上那颗小按钮同一件事；这一栏装着导师时，展开后光标直接落进它的输入框 |

后两条要从 Electron 手里抢回来：无边框窗口没有菜单栏，可 Electron 的**默认菜单**把 `Ctrl+W` 绑成了
「关闭窗口」、`Ctrl+Q` 绑成了「退出应用」，而菜单加速键在浏览器进程里先一步被处理——不换掉那份默认
菜单，应用里连 keydown 都收不到（见 `electron/main.ts` 的 `installAppMenu`）。

改键在**设置 → 输入 → 快捷键**：点「改键」直接按一下组合就换上了，**冲突当场拦下**
（不许和别的功能撞，也不许占用 `Ctrl+C` / `Ctrl+R` / `F12` 这类系统与外壳已经用掉的组合）。
每条能单独重置、也能一键全部恢复默认，改完立刻生效并自动保存。

还有一条规矩：**焦点在输入框里时，不带 `Ctrl` / `Alt` / `Win` 的组合不触发**——否则绑一个字母
就把那个字母打不出来了。

## 语音输入（`lib/voice` + `electron/voice.ts`）

它是**一件内置的功能性插件**（设置 → 插件 → 功能性插件 → 语音输入），**默认关**，
而且**没有模型时开关按不动**（守卫见 `lib/voice/plugin`：拦下来时给的是一句「点进去下载」）。

用起来只有两个动作：点输入框右侧那颗**话筒**（发送键左边）开始录，说完**按空格**结束。
文字**边说边写**：说话途中每约 1.2 秒把这一段音频**整段**重解一次，拿最新全文**替换**输入框里
这一段已经写下的字——文字越写越完整，而不是等停顿才冒出来。录音时按钮左边亮出红点与计时，
点它 / 空格 / 回车都结束，Esc 丢弃这一段（已经写进输入框的字保留）。

分四层，各管一段：

| 层 | 文件 | 干什么 |
| --- | --- | --- |
| 采集 | `voice/mic.ts` | 话筒 → 16 kHz 单声道 Float32（`getUserMedia` + `AudioWorklet`／`ScriptProcessor`）；`drain()` 交出一截采样与这截的峰值电平 |
| 会话 | `voice/session.ts` | 「点一下开始、再点一下（或空格）结束」的状态机 + **整段增量重解**与人声门限；每段的全文交给登记的接收方 |
| 落字 | `lib/composerDoc.ts` 的 `beginVoiceTyping` | 记住这一段落在哪个文本节点、从第几个字符开始；**整段替换**而不是反复 append |
| 按钮 | `components/agent/panel/MicButton.tsx` | 手绘 SVG 的话筒：录音态、计时、音量红点 |
| 推理 | `electron/voice.ts` | 模型下载与 **SenseVoiceSmall** 的识别，跑在**主进程**的 sherpa-onnx 原生运行时里 |

### 为什么是「整段重解 + 替换」，而不是定长切片

模型是 **SenseVoiceSmall**（非流式）：一次吃一段音频、吐一段文字，**音频越长单次解码越慢**。
本机实测（int8 ONNX，CPU，2 线程）：**5.6 秒音频解码 228 ms**（约 24 倍实时），
加载一次约 1.2 秒、之后常驻。

按 1 秒切片看似「实时」，实际上每一片都太短：切不出一句完整的话，还容易让模型对着噪声
「编」出一句本来没有的台词（表现就是「没说话也在出字」）。现在改为**整段累积、增量重解**：
每约 1.2 秒把这一段（从本句开头到现在）整段送一次，拿回来的全文替换上一次写在输入框里的同段文字。
上下文永远完整，后面还能修正前面的词；句子以句末标点收尾并静下来 1.2 秒、或这一段满 12 秒时定稿，
下一句另起一段（`lib/composerDoc` 的 `beginVoiceTyping.update/commit`）。

**静音根本不送识别**（这是不「编字」的关键）：每 100ms 取一次话筒的**峰值电平**，
只看**最近两秒的起伏**——最大值 ≥ 最小值的若干倍、且持续像人声，才算有人在说话。
稳态噪声（风扇、空调、电流声）是平的，再响也不算；纯静音更不算。
门限由「降噪强度」滑杆缩放（设置 → 插件 → 语音输入，0–100）：起伏倍数 1→3.5、
最低峰值 0.0002→0.003、持续块数 1→2，默认 30（中间偏左）。识别不到就往左调，噪声多就往右调。
送识别前还会把段首段尾的静音各裁掉约 200 / 350ms；识别结果若只有标点（模型对着
静音常吐一个「。」），一律当没听见，不会在输入框里留下句号。
两段文字之间中文直接拼接，英文／数字之间补一个空格。

### 为什么推理搬到主进程

2026-11 把能进渲染层的路都试过一遍：

- npm 上的 **sherpa-onnx 是 Node 目标的 wasm**（胶水里 `require("fs")`，Vite 打不进去），
  **transformers.js 不支持 SenseVoice**，官方的浏览器 wasm 只发在 GitHub release 里、要自己
  vendor 十几 MB 进仓库；
- 自己拿 `onnxruntime-web` + 手写前端（fbank / LFR / CMVN / CTC 解码）意味着把**最容易错的那一段**
  重写一遍；线程版 wasm 还要 `SharedArrayBuffer`，而生产页面是 `file://` + 一段 CSP，实测
  `crossOriginIsolated === false`。

所以走**原生**：`sherpa-onnx-node` + `sherpa-onnx-win-x64`（约 23 MB 的 `.node` 与 DLL，
打包时按 `asarUnpack` 解到 asar 外面）。代价是安装包大一点，换来的是官方那份前端与解码。

### GPU 与模型

「GPU 加速」**默认跟着设备走**：启动时问一次 `app.getGPUInfo`，有显卡就开（`provider: 'directml'`）。
运行时不带 GPU 版时会自己退回 CPU（sherpa 内部那条回退），识别照样出字。CPU 上已经够快，
所以这个开关是「有就用上」，不是「不开就没法用」。

模型在那一页下载（约 228 MB）：官方源与国内镜像**并发探测**，谁先应答用谁；
也可以「用本机文件」指一份 `model.int8.onnx`（词表 `tokens.txt` 要放在同一个目录里）。
模型存在 `%APPDATA%\unyra\voice-models\` 下，**不属于任何一份学习数据**。

**音频不出本机、也不写盘**：录到的 PCM 只在那一趟 IPC 里过一下，解完就丢。
